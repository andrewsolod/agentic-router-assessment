# Agentic Router Assessment, Sub-query division

---

## The problem

The notebook's `agentic_rag()` sends every question through one router call that returns exactly
one destination:

```
route_query(q) -> {"action": "OPENAI_QUERY" | "10K_DOCUMENT_QUERY" | "INTERNET_QUERY", ...}
```

One label per question. That holds until the question contains two questions.

Asking *"what was Uber's 2021 revenue and what are the newest LLMs?"* produced this, unmodified:

> 📍 Selected Route: `10K_DOCUMENT_QUERY`
> 📝 Reason: *Asks for Uber's 2021 financial revenue from annual reports; **newest LLMs require
> broader information**.*
>
> — **Uber's 2021 revenue: $17.5 billion**, up 57% YoY. **[1]**
> — **Newest prominent LLMs:** the provided context does not cover LLMs… Recent notable model
> families include GPT‑5, Claude 4, Gemini 2.5, Llama 4, DeepSeek R1, Qwen3.

Two things are wrong, and only one of them is obvious.

1. Retrieval covered half the question, so the second half was answered from the model's weights —
   no retrieval, no citation, no source.
2. **Both halves are delivered in one response with identical formatting and confidence.** The `[1]`
   on the grounded half lends borrowed credibility to the ungrounded one. A reader cannot tell
   which is evidence and which is recall.

The router's own `reason` field says it identified *both* needs. It wasn't a judgment failure —
the response schema had room for one label, so one is what it returned. The fix belongs at the
contract, not the prompt.

## The approach

Split first, route second. Three stages:

```
"uber 2021 revenue and newest LLMs?"
        │
        ├─ split_query()      → ["What was Uber's 2021 revenue?", "What are the newest LLMs?"]
        │
        ├─ answer_one()  ×2   → each sub-query routed and retrieved INDEPENDENTLY
        │                        ├ 10K_DOCUMENT_QUERY → Qdrant 10k_data  → cited answer
        │                        └ INTERNET_QUERY     → web search
        │
        └─ compose            → one response, citations renumbered so they stay distinct
```

**Why splitting is not just about routing.** A combined router returning `["10K", "INTERNET"]` would
not fix this. You would still hold one query string, so you would embed *"uber 2021 revenue and
newest LLMs"* into a single vector sitting between two topics and close to neither, then search both
collections with it. Retrieval quality is decided by the query vector; giving each sub-question its
own focused embedding is the actual win. Routing separately is a consequence.

## What was built

| Function | Job |
|---|---|
| `split_query(user_query) -> list[str]` | Calls the reference `sub_queries()` splitter and parses its output defensively. Never raises. |
| `answer_one(sub_query) -> dict` | Routes one sub-query and returns `{question, action, reason, answer}`. |
| `_shift_citations(text, offset)` | Renumbers `[n]` → `[n+offset]`, reports the highest `n` seen. |
| `agentic_rag_multi(user_query, verbose=True)` | Orchestrates split → answer each → compose. Returns the composed string. |

### Defensive parsing (requirement 3)

`sub_queries()` returns a **string**, not a dict — it is a raw LLM response. It can fail four ways,
and all four fall back to `[user_query]`, which degrades to exactly the original single-route
behaviour:

| Failure | Where it surfaces |
|---|---|
| API error | the `create()` call raises |
| No JSON in the response | `re.search` returns `None` |
| JSON parses, wrong shape | `subQuestions` missing, or not a list |
| JSON parses, empty list | `[]` — passes a naive type check, then yields zero answers and silent output |

The last one is the reason the guard is `not isinstance(subs, list) or not subs` rather than a type
check alone. An empty list is a valid list; it is not a valid split.

The fallback is deliberately the *identity* case. Falling back to the original single query produces
today's behaviour — correct, just not improved. Compare the notebook's own `route_query`, whose
`except` blocks fall back to `INTERNET_QUERY`: that substitutes a *different* behaviour and records
the reason only as prose, so a crashed router and a router that legitimately chose the internet are
indistinguishable downstream.

### Citation renumbering

Each sub-answer is generated by a separate `rag_formatted_response()` call, and each numbers its
sources from `[1]`. Concatenating two such answers yields two different `[1]`s referring to
different documents — invisible to a reader and wrong for any downstream citation check.

`_shift_citations` walks each sub-answer, rewrites `[n]` → `[n + offset]`, and advances `offset` by
the highest number that sub-answer used. First section keeps `[1][2]`; the second's `[1][2]` become
`[3][4]`.

The trace prints `citations shifted by N` per sub-query. That number is internal state with no other
visible symptom — the same category of information whose absence makes a degraded route
indistinguishable from a chosen one.

**Known limitation.** This assumes each sub-answer numbers contiguously from 1, and it does not
deduplicate a source cited by two sub-queries. A complete fix requires `retrieve_and_response()` to
return its retrieved `contents` alongside the answer, so one real source list can be built and
cited once. That is a change to a provided function and was left out of scope.

### Composition is done in code, not by a final LLM call

A synthesis call would read more smoothly. It would also paraphrase, and paraphrasing is where a
citation drifts off the claim it was attached to. Composing in code means every cited sentence is
still the sentence retrieval grounded. Fluency was traded for provenance deliberately.

### Single-query path (requirement 2)

`len(subs) == 1` returns the single answer directly — no composition, no renumbering, no extra LLM
call beyond the split itself.

## Results

All three cases from the assignment's check table:

| Query | Expected | Result |
|---|---|---|
| `"what was uber revenue in 2021?"` | 1 sub-query, 1 route | ✅ |
| `"what was lyft revenue in 2021 and what was uber revenue in 2021"` | 2 sub-queries, both `10K_DOCUMENT_QUERY` | ✅ |
| `"what was uber's 2021 revenue and what are the newest LLMs?"` | 2 sub-queries, **different** routes | ✅ recorded in the notebook |

The third, as recorded:

```
🔀 Split into 2 sub-queries:
   1. What was Uber's 2021 revenue?
   2. What are the newest LLMs?

📍 [1/2] What was Uber's 2021 revenue?
   Route: 10K_DOCUMENT_QUERY  ·  citations shifted by 0
📍 [2/2] What are the newest LLMs?
   Route: INTERNET_QUERY      ·  citations shifted by 1
```

Each half now states which source answered it, and the ungrounded half is no longer smuggled in
beside a citation number it did not earn.

## Running it

```bash
uv venv --python 3.11
uv pip install -r requirements.txt
```

Then select that venv as the notebook kernel. Verify with `import sys; print(sys.executable)` —
the path must be this project's `.venv`, not a system Python. Matching version numbers are not
sufficient; a bare interpreter and a venv can both report 3.11.7 and share no packages.

`requirements.txt` pins `transformers==4.48.0` and `sentence-transformers==3.4.1`. Newer versions
break `nomic-embed-text-v1.5`'s `trust_remote_code` load path.

**Keys** — create `.env` in this folder:

```
OPENAI_API_KEY=sk-...
SERP_API_KEY=          # optional, see below
```

**Vector data** — the notebook reads prebuilt Qdrant collections (`opnai_data`, 20 points;
`10k_data`, 1513 points; both 768-dim) from `Agentic_RAG/qdrant_data`, which ships with the course
repo and is not duplicated here. Copy that directory in, or point `QDRANT_PATH` at it.
It is a file-backed embedded Qdrant, so only one process may hold it at a time.

### The internet route is stubbed

No `SERP_API_KEY` was configured, so `get_internet_content` is replaced by a stub that returns:

> ⚠️ INTERNET route disabled — no SERP_API_KEY set. Router chose this path correctly; only the
> fetch is stubbed.

The stub announces itself rather than returning something answer-shaped. Routing *to* the internet
is exercised and visible in the trace; only the fetch is absent. Supplying a key makes it live with
no code change.
